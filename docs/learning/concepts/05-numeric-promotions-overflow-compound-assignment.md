# JAVA-FND-05 (част 1) — Numeric Promotions, Overflow & Compound Assignment

**Тема:** тип на аритметичните изрази, widening/narrowing primitive conversion, `int` overflow, `byte`/`short` и `+=` срещу `=`.

**Ключови термини:** arithmetic expression type, binary numeric promotion, widening, narrowing, overflow, compound assignment, implicit cast, compile-time error.

## Защо това е важно

В Java типът на променливата, която приема резултата, **не определя автоматично типа на предходното аритметично изчисление**. Това е особено важно при натрупване на бройки, обработка на идентификатори и прехвърляне на стойности между числови типове. Неправилната преценка за overflow може да доведе до грешни стойности без изключение, а съкратените присвоявания могат мълчаливо да загубят информация.

## Mental model за 30 секунди

- **Първо се определя типът на израза и се пресмята резултатът, после той се присвоява.**
- При числово събиране `byte`, `short` и `char` обичайно се повишават до `int` чрез **binary numeric promotion**. Ако операнд е `long`, събирането е в `long`.
- `long total = intValue + 1;` не предпазва от `int` overflow: разширяването до `long` идва **след** събирането.
- `(long) intValue + 1` променя типа на самото изчисление: събирането е в `long`.
- `x += 1` при числови примитиви действа като `x = (T) (x + 1)`, където `T` е типът на `x` (с особеността, че левият операнд се оценява само веднъж). Преобразуването към `T` е **след аритметиката**.
- Стесняващото преобразуване може да загуби информация; `int` и `long` overflow не хвърлят автоматично exception.

## Изпълним пример — Въпрос 5, част 1

```java
public class Main {
    public static void main(String[] args) {
        int max = Integer.MAX_VALUE;

        long a = max + 1;
        long b = (long) max + 1;

        System.out.println(a);
        System.out.println(b);

        byte count = 127;
        count += 1;
        System.out.println(count);
    }
}
```

**Изход:**

```text
-2147483648
2147483648
-128
```

### Стъпките и причинно-следствената връзка

1. `max` има тип `int`; целочисленият литерал `1` също е `int`. Следователно **`max + 1` се изчислява като `int`**. Надхвърля се `Integer.MAX_VALUE` и резултатът се превърта до `Integer.MIN_VALUE`. Чак след това се извършва **widening primitive conversion** към `long`, запазвайки вече отрицателната стойност.
2. В `(long) max + 1` първият операнд вече е `long`. Вторият се повишава и събирането е в `long`, затова резултатът е `2147483648` без `int` overflow.
3. `byte` е 8-битов целочислен тип със знак: диапазон `-128` до `127` (256 представими стойности).
4. При `count += 1` за операцията стойността на `count` се повишава до `int`; резултатът на `127 + 1` е **`int 128`**. Няма `int` overflow.
5. Compound assignment включва **implicit narrowing conversion** обратно към `byte`. При преобразуването `128` става `-128`, защото при `int` → `byte` се запазват ниските 8 бита, които се интерпретират като signed `byte`.

### Защо `+=` и `=` не са едно и също

```java
byte x = 127;
x += 1; // компилира се; x е -128

byte y = 127;
// y = y + 1;         // НЕ се компилира: y + 1 има тип int
y = (byte) (y + 1);  // компилира се; y е -128
```

При обикновено присвояване резултатът `y + 1` е **неконстантен `int` израз** и няма автоматично разрешено стесняване към `byte`. Изричният cast показва, че приемаме евентуалната загуба на информация. За разлика от това `+=` по езиково правило включва преобразуването към типа на лявата променлива.

Важно уточнение: Java допуска стесняващо присвояване за някои **compile-time constant expressions**, когато числовата стойност се побира в целевия тип (например `byte small = 1 + 2;`). Това не важи за `y + 1`, защото `y` е променлива, а не compile-time constant variable.

Спецификацията формулира `E1 op= E2` като еквивалентно на `E1 = (T) (E1 op E2)`, **освен че `E1` се оценява само веднъж**. Това има значение при леви изрази със странични ефекти, например достъп до елемент на масив.

## Практическа последица в backend код

```java
int quantity = Integer.MAX_VALUE;

long broken = quantity + 1;             // overflow преди присвояването
long correct = (long) quantity + 1;     // събиране в long

// При нужда от сигнал за overflow, вместо мълчаливо превъртане:
// int checked = Math.addExact(quantity, 1); // хвърля ArithmeticException
```

При големи стойности прави числовия тип достатъчно широк **преди изчислението**, а не разчитай само на типа на крайния резултат. Когато overflow е недопустим, предпочитай checked операции или валидиране.

## Професионално обяснение за колега / интервю

> В Java типът на аритметичния израз се определя преди присвояването чрез правилата за числово повишаване. Затова `int + int` остава `int` дори резултатът да се присвоява на `long`, и overflow може да настъпи още по време на събирането. Ако първият операнд предварително бъде преобразуван към `long`, изчислението е в `long`. При `byte` и `short` аритметиката често се извършва в `int`. Операторът `+=` включва неявно стесняващо преобразуване на резултата към типа на лявата променлива; обикновеното `=` не прави това за неконстантен `int` израз без изричен cast.

## Текст за слушане

Когато разглеждаме Java аритметика, трябва да разделяме две фази: първо самото изчисление и едва след това присвояването. Важно е какъв тип имат операндите, а не само какъв тип е променливата, в която записваме резултата. Например ако две стойности са от тип int, събирането им обикновено ще е int операция. Дори когато резултатът се записва в long, това не променя вече извършеното събиране. Ако сумата надхвърли максималната int стойност, резултатът може да се превърти към отрицателните числа. Следващото преобразуване към long просто запазва тази грешна за бизнеса стойност в по-широк тип.

Когато първо преобразуваме един операнд към long, работим с по-широк тип още по време на събирането. Точно този момент е решаващ за избягването на overflow в конкретния пример. Друга важна особеност е, че при аритметика с byte, short и char Java обикновено повишава стойностите до int. Така byte плюс числото едно не връща автоматично byte, а int.

Тук се появява разликата между обикновено присвояване и съкратен оператор за присвояване. Ако имаме byte променлива и напишем равно на нея самата плюс едно, Java не разрешава директно присвояване на неконстантния int резултат обратно в byte. Можем да използваме изричен cast, но трябва да сме наясно със загубата на информация. Ако вместо това използваме плюс равно, езикът включва преобразуването обратно към byte като част от операцията. Важно е, че това преобразуване е след събирането, а не преди него.

При стойност сто двадесет и седем плюс едно получаваме int сто двадесет и осем, а при стесняването до осембитов byte крайният резултат е минус сто двадесет и осем. Това не е overflow на самото int събиране, а загуба на информация при narrowing conversion. В реален backend код ключовият навик е винаги да се питаме: в какъв тип се извършва операцията, кога се преобразува резултатът и дали загубата на информация е допустима.
