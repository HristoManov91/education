# JAVA-FND-03 — Object Identity, Logical Equality, String Pool & Null Safety

**Тема:** разликата между идентичност на обекта и логическо равенство, интернирани `String` литерали, `null` и безопасно сравняване.

**Ключови термини:** reference identity, equality, `==`, `equals()`, `Object.equals()`, `String Pool`, `intern()`, `NullPointerException`, null-safe comparison.

## Защо това е важно

В backend приложение често сравняваме идентификатори, входни DTO стойности, стрингове и обекти от persistence layer. Ако объркаме **дали са един и същи екземпляр** с **дали са логически равни**, може да вземем грешно бизнес решение. Друга типична грешка е да извикаме метод през `null` референция и да прекъснем обработката с `NullPointerException`.

## Най-важното за 30 секунди

- При **референтни типове** `a == b` проверява дали двете референтни стойности сочат към **един и същ обект** (или и двете са `null`). Това е *reference identity*. При примитивните типове `==` сравнява примитивните стойности по правилата на типа.
- `equals()` е **инстанционен метод**. `Object.equals()` по подразбиране използва идентичност; класове като `String` го override-ват, за да дефинират **логическо равенство**.
- `String` литералите се интернират. Две срещания на литерала `"Java"` реферират един и същ интерниран обект. `new String("Java")` създава **отделен `String` екземпляр**, независимо от реда на декларациите.
- `null` е допустима референтна стойност, **не обект** и не „липса на стойност на променливата“. `c == null` е безопасно, но `c.equals(b)` при `c == null` хвърля `NullPointerException`.
- При потенциално null референции обикновено ползваме `Objects.equals(a, b)`; ако първият operand е гарантирано non-null, директният му `equals()` също е подходящ.

## Изпълним пример — Въпрос 4

```java
public class Main {

    public static void main(String[] args) {
        String a = new String("Java");
        String b = "Java";
        String c = null;

        System.out.println(a == b);
        System.out.println(a.equals(b));
        System.out.println(c == null);
        System.out.println(a.equals(c));
        System.out.println(c.equals(b));
        System.out.println("END");
    }
}
```

Изпълнението отпечатва **четири булеви стойности**, след което хвърля изключение:

```text
false
true
true
false
```

При `c.equals(b)` възниква **`NullPointerException`**. Следователно `END` **не се отпечатва**, тъй като изключението не е прихванато.

### Механизмът стъпка по стъпка

1. `"Java"` е интерниран литерал. Конструкторният израз `new String("Java")` създава **нов, отделен `String` обект**, който има същото съдържание. `a` сочи новия обект, `b` — интернирания.
2. `a == b` връща `false`, защото това са **два различни екземпляра**. Ако разменим местата на декларациите, резултатът **остава `false`**.
3. `a.equals(b)` връща `true`: `String` override-ва `equals()` и проверява последователността от символи.
4. `c == null` е `true`, понеже `c` съдържа референтната стойност `null`.
5. `a.equals(c)` е `false`, защото receiver-ът `a` не е `null`, а `null` не е логически равен на `String` обекта.
6. `c.equals(b)` не връща `false`; той **хвърля изключение**, защото се опитваме да извикаме инстанционен метод през `null` референция. Последният `println` не се изпълнява.

### Три сравнения, които не трябва да бъркаме

```java
String first = "Java";
String second = "Java";
String third = new String("Java");

System.out.println(first == second);      // true: един интерниран обект
System.out.println(first == third);       // false: new създава друг обект
System.out.println(first.equals(third));  // true: еднакво съдържание
```

Важно: `String Pool` **не означава**, че `new String(...)` ще върне съществуващия обект. Изричното `new` различава този случай от повторното използване на интерниран литерал. При нужда `intern()` може да върне каноничната интернирана референция, но това не променя идентичността на вече създадения с `new` обект.

### Null-safe сравнение

```java
import java.util.Objects;

String left = null;
String right = "Java";

boolean same = Objects.equals(left, right); // false
```

При `Objects.equals(left, right)`: и двете `null` дават `true`; само едната `null` дава `false`; при два non-null аргумента се използва `left.equals(right)`. Ако имаме известна константа, `"Java".equals(possiblyNull)` също е безопасно, защото receiver-ът е гарантирано non-null. `== null` е подходящата директна проверка дали дадена референтна променлива сочи обект.

## Професионален отговор (за колега или интервю)

> В Java `==` при референтни типове сравнява идентичността на обектите, а `equals()` е метод, чиято семантика се определя от съответния клас. `String` го override-ва за сравнение по съдържание. String литералите се интернират, но `new String("Java")` създава отделен обект, затова сравнение с `==` срещу литерала дава `false`, а с `equals()` — `true`. `null` е референтна стойност, която не сочи обект; извикване на инстанционен метод през нея причинява `NullPointerException`. За null-safe логическо сравнение на две потенциално null променливи използвам `Objects.equals()`.

## Текст за слушане

В Java първо трябва да разграничим идентичността на обект от логическото равенство между обекти. Две променливи могат да сочат към един и същ обект. В такъв случай при референтните типове операторът двойно равно, или equals equals, връща истина. Но две променливи могат да сочат към различни обекти, които имат еднакво логическо съдържание. Тогава операторът двойно равно връща неистина, въпреки че извикването на метода equals може да върне истина.

Методът equals не сравнява автоматично съдържанието на всеки обект. Неговата базова реализация в клас Object проверява идентичност. Класът String обаче дефинира равенството чрез последователността от символи. Ето защо два различни String екземпляра могат да бъдат равни според метода equals.

Отделно има механизъм за интерниране на String литералите. Когато срещаме един и същ литерал Java на няколко места в програмата, променливите могат да получат референция към един и същ интерниран обект. Но ако изрично напишем new String с този литерал, създаваме друг екземпляр със същото съдържание. Редът на декларациите не отменя действието на new.

Накрая, null е стойност на референтна променлива, която не сочи към обект. Проверката дали референцията е null е безопасна. Но когато опитаме да извикаме инстанционен метод през такава референция, получаваме NullPointerException. Ако искаме да сравним две променливи, за които не знаем дали са null, можем да използваме Objects.equals. Така избягваме излишни проверки и ясно заявяваме намерението си да сравним стойностите по логическо равенство.

Практическото правило е просто: определяй дали търсиш идентичност на екземпляра или логическо равенство. После избери подходящото сравнение и вземи предвид null референциите. Това прави Java кода по-предвидим и по-лесен за ревюиране.
