# Име на темата

> Целта на всеки модул е да бъде едновременно **мини учебна глава** и **изпълнима лаборатория**. README не трябва да е само кратко резюме, а да обяснява какво, защо, как работи под капака и как го доказва кодът.

## Какво ще научим

Кратък списък с конкретните инженерни знания, които лабораторията демонстрира.

## Mental model / голямата картина

Обясни темата така, че човек да разбере проблема още преди да види API-то:

- какъв исторически/production проблем решаваме;
- кои ресурси или ограничения участват;
- какви са основните термини;
- как се променя mental model-ът спрямо по-стария подход.

Когато помага, добави ASCII diagram / flow / before-after схема.

## README → код

> Тази секция е задължителна за всеки учебен модул.

Направи карта между основните концепции в README и конкретните файлове, които ги демонстрират. Използвай **относителни Markdown линкове**, за да работят и след clone на repository-то.

| Концепция | Production-like пример | Доказателство / тест |
| --- | --- | --- |
| Основна техника | [`ExampleService.java`](./src/main/java/.../ExampleService.java) | [`ExampleServiceTest.java`](./src/test/java/.../ExampleServiceTest.java) |
| Конфигурация | [`application.properties`](./src/main/resources/application.properties) | — |

Освен общата карта, във всеки README раздел, който обяснява конкретна implementation идея, сложи линк към съответния class/config/test непосредствено до обяснението.

## Проблемът

Опиши реален scenario, а не само definition. Добре е да има числа, latency, resource limits или примерен request flow, когато темата го позволява.

## Защо възниква

Обясни какво се случва под капака. Не прескачай директно към „good code“.

Читателят трябва да може да отговори:

1. Защо старият/наивният подход е проблем?
2. Къде точно е bottleneck-ът или correctness рискът?
3. Как новата техника променя lifecycle/resource model-а?

## Термини

За теми с нов vocabulary добави кратка таблица с точни значения. Например thread/task/scope/context, persistence context/session/transaction и т.н.

## Значими варианти на новото API / техника

Когато **темата, която в момента учим**, предлага няколко съществени стратегии, policy-та, режими или implementation подходи, не показвай само варианта, който сме избрали в кода.

Задължително обясни локално в учебния материал:

- кои са основните practically relevant варианти;
- как се различава поведението им;
- какво връщат / как завършват, когато това е част от API contract-а;
- как реагират при failure/cancellation/timeout, ако това е важно за темата;
- кога бихме използвали всеки вариант;
- защо текущият пример избира точно един от тях;
- какво би се променило, ако изберем друга стратегия.

Добави и линк към **официалната version-specific документация**, но линкът е допълнение, а не заместител на обяснението в repository-то. Идеята е след месеци README/кодът сам по себе си да е достатъчен за припомняне, а официалната документация да служи за по-дълбока справка.

Пример: ако учим `StructuredTaskScope.Joiner`, сравни `awaitAllSuccessfulOrThrow()`, `allSuccessfulOrThrow()`, `anySuccessfulResultOrThrow()`, `awaitAll()`, `allUntil(...)` и custom Joiner, вместо да споменеш само policy-то от текущия пример.

Това правило важи за **новата изучавана концепция**, а не за всяко познато Java API. Не превръщай материала в копие на JavaDoc и не описвай механично всички overload-и на неща като `String.substring()`.

## Bad / наивен вариант

Покажи код или flow и обясни **защо** изглежда логичен, но има недостатък.

## Good / препоръчан вариант

Не показвай само крайния код. Разбий го стъпка по стъпка:

- защо този class е тук;
- защо точно тук е boundary-то;
- защо тази операция е concurrent/sequential/transactional;
- какво гарантира конкретното API;
- какво би се счупило, ако махнем важен ред.

## Как го доказваме

Тест, измерване, логове или възпроизводим експеримент. Линкни директно тестовете/benchmark файловете.

Предпочитай тестове, които доказват **семантиката на темата**, а не само „Spring context starts“.

### Изпълними HTTP примери

Ако учебният модул expose-ва REST endpoint-и, README не трябва само да изписва URL-а. Направи проверката удобна директно от IntelliJ:

- добави physical `.http` файл в модула, например `http/demo.http`, с готови GET/POST/PUT/DELETE заявки;
- до обяснението в README сложи относителен линк към конкретния `.http` файл;
- за проста заявка добави и `bash`/`curl` fenced code block, който IntelliJ може да разпознае като runnable command от Markdown;
- под заявката добави сгъваем `<details>` блок с **примерен резултат**, за да може материалът да се чете и без стартирано приложение;
- ако response съдържа динамични стойности (thread id, timestamp, UUID и т.н.), отбележи изрично, че те ще се различават;
- при по-сложни заявки с headers, JSON body, authentication или няколко стъпки `.http` файлът е основният runnable пример, вместо да превръщаме README в огромна `curl` команда;
- не commit-вай secrets в `.http` файловете; използвай HTTP Client variables/environment files, когато са нужни credentials.

Целта е читателят да има три режима: **прочитам обяснението → виждам примерен response → пускам реалната заявка с един Run action в IntelliJ**.

## Преди / след

Сравни не само броя редове, а:

- ownership/lifecycle;
- correctness;
- latency/throughput;
- resource usage;
- observability/debuggability;
- complexity/trade-offs.

## Production considerations

Задължително отбележи какво техниката **не решава**. Например нов concurrency API не премахва DB pool limits; ORM optimization не оправя лош индекс и т.н.

## Кога не си струва

Случаи, в които техниката усложнява системата без достатъчна полза.

## Коментари в Java кода

> Учебните модули нарочно имат повече коментари от типичен production repository.

За ключовите класове и нетривиалните участъци добавяй български JavaDoc/inline коментари, които обясняват:

- **защо class-ът съществува**;
- защо кодът е на това архитектурно ниво;
- lifecycle/ownership/cancellation/transaction boundaries;
- какво гарантира API-то;
- защо конкретен ред е важен;
- какво би станало при алтернативния подход;
- връзката с README, когато е полезна.

### Explicit типове вместо `var`

В `education` repository-то **не използвай Java `var`** в нашия production-like код, тестове или учебни code snippets.

Изписвай explicit типа, особено когато резултатът идва от API, което в момента учим. Така при четене в IntelliJ веднага се вижда contract-ът на метода без да е нужно hover/inference.

Примери:

```java
StructuredTaskScope<Object, Void> scope = StructuredTaskScope.open();

StructuredTaskScope.Subtask<List<Account>> accountsTask =
        scope.fork(() -> accountClient.getAccounts(customer.id()));

ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
```

Това правило е умишлено по-строго от typical production style. Целта на repository-то е **учене и припомняне**, затова visibility на типовете е по-важна от няколко спестени символа.

Ако цитираме външен код verbatim като исторически/официален пример, може да запазим оригинала, но нашият собствен runnable/production-like вариант трябва да използва explicit types.

### Английски технически термини в обясненията

Когато в README, JavaDoc или inline коментар използваме английски технически термин, който не е очевиден от самия Java/API синтаксис, при първата му поява добавяй кратко българско пояснение в скоби. Целта е да запазим реалната терминология, която ще срещаме в документация и код ревюта, но материалът да може да се чете без предварително знание на английския термин.

Примери:

- `sibling operations` (паралелни операции на едно и също ниво с общ parent);
- `request identity` (идентичност на конкретната заявка, например нейния `requestId`);
- `fan-out` (разклоняване към няколко независими операции);
- `fan-in` (събиране на паралелните резултати обратно в един поток);
- `ownership` (кой компонент притежава и управлява lifecycle-а на задачата);
- `lifecycle` (жизнен цикъл);
- `downstream service` (услуга, която текущият компонент извиква);
- `fail-fast` (спиране при първата релевантна грешка).

Не превеждай механично Java keywords, имена на класове/методи или официални API identifiers като `StructuredTaskScope`, `ScopedValue`, `fork()` и `join()`. Ако терминът вече е обяснен непосредствено преди това, не повтаряй скобите на всяко следващо изречение.

Не коментирай механично очевидното (`// increment i`). Коментарът трябва да добавя инженерно знание, което не се вижда само от syntax-а.

Ключовите source и test файлове трябва да могат да се четат самостоятелно в IntelliJ и пак да дават достатъчно контекст.

## Как да стартираме примера

Команди, prerequisites, VM flags, примерни requests и какво точно да наблюдаваме в output/logs.

## End-to-end walkthrough

За multi-class/multi-service тема добави поне един пълен walkthrough от входа до резултата:

```text
request/event
→ boundary
→ orchestration
→ important internals
→ result
→ cleanup/lifecycle end
```

## Какво да запомня

Най-важните 8–15 извода от темата. Това трябва да работи като quick revision след месеци.
